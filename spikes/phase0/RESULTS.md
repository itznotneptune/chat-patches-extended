## Findings
- **F-1 (V-59.4, P12 exact-name reflection).** On the first pass, the `bool` conflict mod made the self-check bind the **wrong** field. When another mod adds a same-named `@Unique` field to `ChatScreen`, Mixin renames Chat Patches' own field (for example `fde30cff$chatpatches$showSearchBar$0`, with a hash that changes per launch), so the exact name pointed at the foreign field. With the `int` variant, the JVM holds two same-named fields of different types. **Engineering decision (within P12):** an exact-name lookup is accepted only if there is exactly one match **and** no `$chatpatches$<name>$` renamed variant exists; otherwise Class Q fallback. After hardening, both variants fall back (clean re-run).
- **F-2 (P10 layering).** In 1.21.11, Fabric's `ScreenEvents.beforeRender` runs inside `Screen.renderWithTooltipAndSubtitles`, which already advances the GUI strata twice before `render`. The probe recorded the window in stratum 3 and `ChatScreen.render` in stratum 5, so the `beforeRender` path is beneath all chat-screen UI by construction. The HUD path recorded the same strata.
- **F-3 (tooltips).** `ScreenEvents.afterRender` runs **after** `renderDeferredElements`, so a tooltip set there would only appear on the next frame. The Extended tooltip therefore calls `nextStratum()`, `setTooltipForNextFrame(...)` and `renderDeferredElements()` itself in `afterRender`; V-07 confirms the same-frame result.
- **F-4 (hit-test boundary, V-54).** Chat Patches' `getEoEIndex` (the inlined vanilla `getMessageEndIndexAt`) treats the exact coordinate `y = guiHeight − 40` as main-chat line 0, but nothing is drawn on that GUI row. This is a zero-width boundary: only an integer mouse coordinate exactly on that edge is affected. The final V-54 clicks pixel centres, which is how the sampled pixel is defined. No production change is needed; noted for the production hit-test.
- **F-5 (context-menu geometry).** The Chat Patches context menu's `isMouseOver` box is larger than what it draws, and it includes the search button. For pixel scans, the menu's drawn area is the union of its button widgets, excluding the search button.

## Engineering decisions and test fixes (no escalation needed, per §13.7 last paragraph)
- Loom 1.18.4 with Gradle on JDK 25 and a JDK 21 toolchain; full Fabric API on the spike runtime; explicit YACL nested dependencies in dev.
- F-1 reflection hardening (above).
- V-55: the expected visibility is evaluated from the state at the end of the frame. Sampling it before the tick's `setScreen` produced 39 false anomalies on the first pass.
- V-53: the scan uses the rectangles each element actually fills (not EditBox bounds) and excludes the blinking-cursor cell; the context menu uses F-5's geometry. On the first pass, the wrong rectangle made the input and search scenes report false failures (sampled pixels were 127,0,127, i.e. darkened, so the window was behind).
- V-07/V-57/V-58/V-09e: the window was moved to an area no protected element covers (right of the main chat). On the first pass it overlapped the main chat, so input was correctly treated as protected (P11), and a right-click opened Chat Patches' context menu, contaminating later steps.
- V-54: sample and click at pixel centres (F-4).
- V-20m.noRelog: the first-pass check matched `cpx#SWAP` inside `cpx#SWAPDUPE`. The exact-text count was 0 on both passes.
- `setCursorPos` is called on the gametest thread, not the client thread.

## Coverage gaps (not run, or run only in part)
- **V-01:** the `-Dmixin.debug.export=true` class dump was not produced; V-01 rests on the capture assertions only.
- **V-27f:** plugin-style and boundary messages were not in the compared set (say, system, `x3`, player only).
- **V-04c:** the "restored `x3`" case was not run.
- **V-20m:** context-menu **copy** and **regex** search were not exercised (delete and plain search were).
- **V-15:** not run; the spike used the full Fabric API rather than only the declared modules.
- **V-35:** only the Chat Patches pin was tested; the Java and other-Minecraft-version rejections were not.
- **V-36:** only fault injection, for one Class S member (RESTORED_TAG → degraded) and the condensation read (V-04c.fault → superset fallback); the other adapter members were not fault-injected. The stub-jar variant is deferred to Phase 8, as planned.
- **V-53:** the "without `nextStratum()`" comparison was not re-run after the metric fix. The earlier `s2probe` run used the faulty metric, so its input-scene failures are superseded.
- **V-54:** 60 points over one overlap scene, not a 20×20 grid per V-53 scene.
- **V-55:** transitions were driven with `setScreen`, not key presses.
- **C-Q36** (V-20l, V-20p, V-20n, V-62, V-21e) remains a checkpoint before Phase 7, as planned.
