# Chat Patches Extended — Decision Register

Project: **Chat Patches Extended** (`cpextended`), an independent, unofficial client-side companion mod for Chat Patches. Previously referred to as *Chat Patches Tabs* (working name, superseded by D12/Q13).
Baseline: Minecraft 1.21.11 · Fabric · Chat Patches `8.0.0` (published jar `chatpatches-8.0.0+1.21.11-fabric.jar`; source commit `987cf24`).

## 0. Decision governance (owner directive, 2026-10-18)

1. All approved decisions (D, F, Q, P and clarifications) are **authoritative requirements**. *(Directive issued 2026-10-18 and reaffirmed with the P15 approval.)*
2. Routine technical and implementation-design decisions are made **under delegated engineering authority**, choosing the most maintainable, reliable, compatible and conservative option. They're documented with reasoning as **ED** entries, and minor ambiguities as **A-n** assumptions. Both must not contradict approved requirements.
3. **Escalate only when:**
   - approved requirements directly conflict;
   - a decision would materially change player-visible behaviour;
   - a decision could introduce meaningful data-loss, privacy or security risk;
   - a necessary implementation can't satisfy an approved requirement;
   - a previously approved architectural constraint would have to change;
   - multiple viable choices represent **substantially different product behaviour**, not interchangeable engineering techniques.

   Each escalation states the precise issue, the affected approved decisions, why engineering judgment can't resolve it, the minimum owner decision required, and a recommendation with its trade-offs.

   **Routine matters decided by engineering judgment** (examples from the owner, 2026-10-18): internal class and method organization; data structures and caching; routine error handling; efficient event processing; GUI details that don't materially alter approved behaviour; test organization; minor configuration mechanics; compatibility techniques within approved architectural boundaries.

   Each escalation explains why the requirements are insufficient and why engineering judgment can't resolve it safely. Related questions are grouped.
4. Settled decisions aren't reopened without concrete evidence of a conflict.
5. Design ≠ source-verified ≠ runtime-verified. Verification is never claimed without execution.
6. Delegated design authority **doesn't** authorize implementation, Minecraft tests or verification spikes; those need separate owner approval.

## 1. Approved decisions

### 1.1 Core and feature decisions (approved earlier, unchanged)

| ID | Title | Approved decision | Key constraints |
|---|---|---|---|
| **D1** | Main chat behaviour | Keep the Chat Patches main chat unchanged; add customizable windows and tabs; don't replace Chat Patches' main chat. | Search, timestamps, dupe condensation, context menus and chat logging stay Chat Patches'. D2 hiding (and the Q2 restoration it requires) are the only exceptions. |
| **D2** | Message visibility | Messages matching a tab's rules may be hidden from the main chat using the **"not admitted"** approach. | Hidden messages stay in Chat Patches' saved log when logging is on. No inconsistencies with search, dupe condensation or context menus. Accepted: hidden messages are excluded from main-chat search and dupe counters. Safety fallback: never invisible everywhere. Needs runtime validation. |
| **D3** | Message retention | Mirror Chat Patches' existing history; no independent persistent database. | References to existing objects where feasible; follow Chat Patches' limits and clearing; F1 references allowed for hidden messages. |
| **F1** | Hidden-message references | Session-only references for messages excluded from the main chat. | No persisted copy; clearing and retention synchronized with Chat Patches. |
| **F2** | Meaning of "underlying history" | Saved chat log only. | Hidden messages need not stay in main-chat lists; preserved in the saved log when logging is on; logging-off behaviour documented. |
| **F3** | Hide configuration | Per-tab hide toggle with safety fallback. | Hide only when at least one configured destination can display the message; document overlaps, disabled tabs, closed windows and config changes; deterministic visibility. |
| **F4** | Chat Patches integration | A small compatibility adapter. | Centralize version-sensitive interactions; minimal direct dependencies; Fabric events where appropriate; minimal Mixins; documented integration points. |

### 1.2 Resolutions of open questions Q1–Q14 (approved 2026-10-18)

| ID | Title | Approved decision |
|---|---|---|
| **Q1** | Restored-message filtering | Remove recognizable Chat Patches-added formatting before matching restored messages. **An explicitly approved exception to D5.** Reconstruction limitations and ambiguous cases must be documented. |
| **Q2** | Orphaned hidden messages | When a configuration change would make previously hidden messages inaccessible, **restore them to the main chat in chronological order after user confirmation.** |
| **Q3** | Duplicate condensation | Preserve main-chat visibility when an incoming duplicate causes Chat Patches to merge away a previously visible message. **The replacement must not be hidden in that situation.** |
| **Q4** | History restoration | Restored-history behaviour is configured **independently for each tab**. |
| **Q5** | Version compatibility | Require explicitly tested Chat Patches versions. Initially **only Chat Patches 8.0.0 on Minecraft 1.21.11/Fabric.** Don't silently accept untested versions. |
| **Q6** | GUI framework | A **fully custom Minecraft GUI** for all configuration and window management. **YACL not required.** |
| **Q7** | Unread counters | A message is unread when its destination tab is **unselected** or its **window is hidden**. A selected tab in a visible window counts as read, including during gameplay. |
| **Q8** | Tab ownership | Each tab belongs to **exactly one window** and can be moved between windows. Moving preserves the tab's identity, configuration, history and unread state. |
| **Q9** | Filter changes | Filter changes affect **future messages only**. Existing tab contents and historical routing aren't rebuilt. |
| **Q10** | Boundary lines | Chat Patches-generated boundary lines are **exempt from filtering** and preserved in the main chat. |
| **Q11** | Rendering and input priority | **Chat Patches' actual interactive regions** take rendering and input priority over overlapping Extended windows. Interaction with Extended windows elsewhere on the chat screen isn't blocked. |
| **Q12** | Message normalization | Preserve original incoming text: no trimming, whitespace normalization, punctuation removal or stripping of Minecraft formatting codes. Apply only the filter's configured case sensitivity. **Literal and Regex are case-insensitive by default.** Q1's restored-history exception is preserved. |
| **Q13** | Project identifiers | Java package `io.github.itznotneptune.cpextended` · Maven group `io.github.itznotneptune` · mod ID `cpextended` · public name Chat Patches Extended · license LGPL-3.0. |
| **Q14** | Invalid filters | An invalid filter **suspends its entire tab.** A suspended tab must not hide incoming messages. |
| **Q14.1** | Validation rules | (1) Maximum pattern length **1,024 characters**. (2) **Regex safety:** a researched, demonstrably enforceable bounded-matching strategy is required before implementation; Java's regex engine must not be assumed to provide a step limit. (3) GUI shows **inline errors and prevents saving** invalid filters. (4) Switching Literal/Regex **preserves the pattern text exactly** and revalidates. Retained behaviour: empty patterns invalid; unknown modes invalid; invalid hand-edited files never silently repaired. |

### 1.3 Resolutions approved in the latest review (Q15, Q17–Q23)

| ID | Title | Approved decision |
|---|---|---|
| **Q15** | Regex engine | **Literal-only initial release.** Regex mode is deferred until a demonstrably bounded implementation is approved. RE2/J remains a *proposal* for that later approval; no regex engine is approved. (Recorded from the owner's statement "preserve the approved Literal-only initial release", 2026-10-18.) |
| **Q17** | Suspended tabs | Preserve existing history **read-only**; stop new routing and hiding; display configuration errors. Suspension isn't deletion and **doesn't trigger orphan restoration**. |
| **Q18** | Input priority | **Vanilla chat input, command suggestions, visible main-chat message lines and Chat Patches' interactive regions** take priority over overlapping Extended windows. **Invisible or inactive regions must not intercept input.** Windows stay interactive in unobstructed regions. |
| **Q19** | Hidden windows | Explicitly hidden or disabled windows, **F1** HUD hiding, and **Chat Visibility: Hidden** all count as hidden *for unread purposes*. Hidden windows **keep routing and applying approved filters**; they aren't suspended. |
| **Q20** | Configuration access | **Optional** Mod Menu integration plus a configurable keybind, **unbound by default**. Mod Menu isn't required. |
| **Q21** | Tab movement | Both config-screen movement and **drag-and-drop between windows**. Tab identity, filters, history and unread state are preserved. **Moving doesn't trigger orphan restoration.** |
| **Q22** | Orphan restoration | Respect Chat Patches' history cap. Restore in chronological order and **disclose potential pruning**. Restore only outside the chat screen or at a verified safe point. **Cancelling aborts the entire change.** Verify pruning consequences and recoverability through Chat Patches' saved log. |
| **Q23** | Unread counters | Restored history doesn't add unread. **Condensed duplicates count once per displayed tab entry**, not per incoming occurrence. Pruning unread entries reduces unread; **unread can't exceed retained unread entries.** Verify how condensation can be reliably detected. |

- **D6.1** (Literal and Regex modes) stays approved as the long-term design. Q15 defers its Regex half: in the initial release, a filter with `"mode": "regex"` is a *recognized but unsupported* mode, so it's invalid and suspends its tab (Q14/Q17).
- **Q14.1(2)** is satisfied trivially in the initial release, since no regex runs.

### 1.3b Q24–Q30 (approved 2026-10-18)

| ID | Title | Approved decision |
|---|---|---|
| **Q24** | Disabled windows | Tabs in explicitly **disabled windows keep receiving** matching messages but **stop hiding new messages**. Previously hidden messages stay in their tabs and become accessible on re-enable. **Only deletion triggers orphan restoration.** F1 and Chat Visibility don't affect hiding rules. |
| **Q25** | Unread when moving tabs | Into a **populated** window: unread preserved while the moved tab stays unselected. Into an **empty, visible** window: the tab is auto-selected and unread is cleared. Into a **hidden** destination: unread preserved. *An explicit exception to Q21's unread preservation.* |
| **Q26** | F1 | F1 hides Extended windows during gameplay. When the chat screen opens, windows become **visible and interactive even under F1**. F1 counts as hidden for unread **only while the chat screen is closed**. Disabled windows and Chat Visibility: Hidden remain separate conditions. |
| **Q27** | Orphan-restoration safety | **Block** an orphan-producing change if restoring would immediately prune **any orphaned message** that lacks a **verified durable recoverable copy**. Ordinary history pruning stays permitted. Respect Q22's cap and chronological order. Don't assume Chat Patches' saved log retains pruned messages. |
| **Q28** | Saving with invalid filters | Valid unrelated changes may be saved while existing invalid filters remain; those filters are preserved **unchanged**, their tabs suspended and errors shown. **Newly introduced or modified invalid filters can't be saved.** Invalid filters never execute. Q15 Literal-only is maintained. |
| **Q29a** | Global search | **Reuse Chat Patches' search field** to search the main chat and **all Extended tabs** simultaneously. Each tab shows matches from its own history. Search is a **display filter**, not routing. Clearing it restores the normal view. Search never modifies stored history, routing filters or unread. **No separate search fields** in Extended windows. |
| **Q29b** | Search-field priority | Protect Chat Patches' search-field region **only while the field is actually visible**, detected through the adapter. **If detection fails, conservatively reserve the region while search is enabled.** Investigate accessor/mixin vs. reflection. Q18 stays intact. |
| **Q30a** | Stacking | Windows initially stack in configuration order; the **last interacted** window comes to the front, subject to protected vanilla and Chat Patches regions. |
| **Q30b** | Drop targets | Only the **topmost visible, unobstructed destination tab strip** accepts a dragged tab. |
| **Q30c** | Dropping outside windows | Dropping a tab **outside existing windows creates a new window** containing it. Dropping on its **source window does nothing**. Identity, configuration, history and applicable unread state are preserved. **No orphan restoration.** |
| **Q30d** | Hidden destinations | Hidden or disabled windows **can't receive dragged tabs**; they remain destinations through the config GUI. |
| **Q30e** | Empty windows | Moving the final tab out leaves the window intact **until manually deleted**. |

### Q37 — Can a player edit lift a runtime suspension mid-session? (P9) — *Deferred enhancement (owner, Phase 8, 2026-10-19)*
- **Owner decision (Phase 8 authorization):** for the initial release the **relaunch-only baseline is retained**: a runtime-suspended tab recovers only after restarting the client. No automatic recovery, save-triggered recovery or manual retry button in the initial release. Q37 is recorded as **deferred enhancement work** and is **not a release blocker**. Options (b) and (c) below remain candidates for a later release.

- **Why it needs you:** P9 approves that a runtime-suspended tab stays suspended with **no automatic recovery**, and the documented recovery is **relaunch**. You didn't specify whether an *intentional* player action should lift it earlier, and P9 forbids inventing one without approval.
- **Options:**
  - **Current baseline (unchanged, per owner instruction 2026-10-18):** runtime suspension lasts **until relaunch**. No retry button, automatic recovery or save-triggered recovery may be introduced until Q37 is decided.
  - **(a) Recommended:** relaunch only. This is the simplest, and a runtime failure on a *valid* filter suggests a bug that an edit may not fix.
  - **(b)** An intentional save of that tab's filters in the GUI (or a reloaded file) re-validates them and lifts the runtime suspension. A new failure re-suspends with a fresh warning key.
  - **(c)** An explicit "Retry tab" button on the error marker, rate-limited to once per session per tab.
